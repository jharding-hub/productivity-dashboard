### 1.2 Dashboard Data — Firestore `users/{uid}/data/dashboard`

One JSON blob in a single document (`legacy.js:1034`, `:1151`). Contains `state` serialized to a
string. Includes tasks, projects and subtasks, notes, reminders, timeline blocks, brain-dump
thoughts, routines, points/streak counters, settings (theme, `supportLevel`, `focusMode`,
stop-motion), workout/gym routine selections, and `_tombstones` (a grow-only map of deleted item
ids → deletion timestamp).

Explicitly **excluded** from this blob and split into their own documents: `checkins`, `moodLog`,
`completedTasks`, `completedTasksLifetime`, `completedProjectSubtasksLifetime`, `remindersArchive`,
`remindersArchiveLifetime` (`legacy.js:1151`).

### 1.3 Wellness Data — the consumer-health-data core

| Document | Path | Schema | Source |
|---|---|---|---|
| Check-in log | `users/{uid}/data/checkins` | `{v:1, items:[…], updated}` | `legacy.js:7172`, `:7193` |
| Mood log | `users/{uid}/data/moodLog` | `{v:1, entries:[…], updated}` | `legacy.js:7204`, `:7224` |
| Journal | `users/{uid}/data/journal` | Encrypted — see §5 | `legacy.js:9396`, `:9417` |

**Check-in entry shape** (`_logCheckIn`, `legacy.js:7082`):
`{ id, ts (ISO), type, …payload }`, capped at 500 entries (`CHECKIN_LOG_MAX`).

Four `type` values are written:

| `type` | Payload | Written at | Health-data character |
|---|---|---|---|
| `urge` | `{urgeType, urgeLabel, note?, delayMinutes, outcome}` | `legacy.js:7673` | **Consumer health data.** Impulse-control episode + outcome. |
| `halt` | `{items:[…addressed], count}` | `legacy.js:7455` | **Consumer health data.** Hunger/anger/loneliness/tiredness + sensory state. |
| `breath` | `{techniqueId, techniqueName, cycles}` | `legacy.js:5644` | **Consumer health data.** Bodily-function intervention (breathing). |
| `grounding` | `{techniqueId, techniqueName}` | `legacy.js:3554` | **Consumer health data.** Mental-health self-regulation intervention. |

**Urge types collected** (`URGE_TYPES`, `legacy.js:7539`): `buy` (impulse buy), `phone`
(phone/social media), `snack` (snack/food), `skip` (skip a task), `other`. Delay options: 5, 10, 20
minutes. Outcome: `passed` | `acted`.

> **Positioning note, load-bearing for the whole document set:** the urge categories are
> *impulse-control-for-productivity* categories — spending, screens, snacking, task avoidance.
> None are substance-use or self-harm categories. This materially supports the "general wellness,
> not treatment" position, and the documents should describe the feature accurately in those terms
> rather than in recovery/clinical terms. The free-text `note` field on `other` is unconstrained
> and could contain anything, which is why it is classified as sensitive regardless.

**Mood log entry:** keyed by local day, one entry per date (`legacy.js:4880`), recording energy
level and mental state. The advice map (`legacy.js:3463`) pairs energy × state into a suggestion
string — this is an **inference about mental state**, which is squarely consumer health data under
MHMDA.

### 1.9 Error reporting — Sentry

**Not named in the original brief, but it is a live subprocessor.** `@sentry/react`, initialised in
`src/main.jsx:41`.

Configured defensively and correctly:
- `dataCollection.userInfo: false`
- `dataCollection.httpBodies: []`
- `dataCollection.genAI: { inputs: false, outputs: false }`
- Localhost and private-range hosts never report (`main.jsx:25`–`:35`)
- `beforeSend` drops known-benign WKWebView IndexedDB noise

Residual exposure: exception **messages and stack traces** are still transmitted, and an exception
message can incidentally embed user content (e.g. a task title inside a thrown string). This is a
low-likelihood, non-zero path. See COMPLIANCE-GAPS.md **G-08**.

CSP violation reports are also sent to Sentry (`public/_headers`, `report-uri`).

## 2. What reaches the LLM

Axis is proxied through `centerpost-jarvis` → the Anthropic API (model
`claude-haiku-4-5-20251001`). The Worker verifies a Firebase ID token before forwarding
(`jarvis-worker.js`).

**Confirmed content sent to the model:**

| Feature | Payload | Source |
|---|---|---|
| Brain-dump organise | All brain-dump thought texts + existing project names | `legacy.js:2991`, `:3002` |
| Note → action items | Note title + first 800 chars of body + tagged project names | `legacy.js:3279`, `:3289` |
| Axis chat | The user's typed or dictated message | `legacy.js:12834`+ |
| Ops chat | Operator-only, `{message}` shape | `jarvis-worker.js:1046` |

**Journal, check-ins, mood log, and urge logs are NOT bundled into any AI prompt as context.**
Verified by inspecting all `_jarvisAuthHeaders()` call sites — none reference `state.checkins`,
`state.moodLog`, or the journal document. This is a genuinely good finding and the documents may
say so.

**However:** Axis chat is free-text. A user may type anything, including health-adjacent content
("I keep getting the urge to…", "I'm feeling awful today"). Health-adjacent content therefore
**can** reach the LLM, by the user's own action rather than by the app's design. The privacy
policy and AI disclosure must say this plainly.

**Training-use status:** Anthropic's Commercial Terms of Service provide that inputs and outputs
submitted through the API are not used to train its models. **This must be re-verified against the
current terms at drafting time and cited with a date** — it is a factual claim about a third party
and must not be asserted from memory. Marked **UNVERIFIED** pending that check.

**Human review:** Joe (as operator) can see the first 100 characters of prompts that trip the
injection-pattern scanner, delivered by Guardian email (`guardian-worker.js:283`, `:433`). That is
human review of user input and must be disclosed.

- Breathwork and grounding completion records — same

- Child chore data including the "Take meds" item — `kids` doc

Email address, Firebase UID, Google account identifier, `createdAt`/`lastActive`, `invitedWith`,

`aispend:{date}` aggregates, `AI_MODEL_RATES`, SendGrid aggregate stats, service-worker cache

## 5. Retention and deletion — reality check

### What deletion actually does today

In-app path exists: Settings → destructive confirm typing "Delete my account"
(`legacy.js:620`) → `POST /account/delete` on Jarvis (`legacy.js:653`) →
`handleAccountDelete` (`jarvis-worker.js:987`).

It deletes, in order:
1. `users/{uid}/data/{dashboard, checkins, completedTasks, remindersArchive, journal, moodLog,
   profile, kids}` (`USER_DATA_DOCS`, `:985`)
2. `users/{uid}` profile doc
3. KV `tier:{uid}`, `rl:{uid}`, `aiq:{uid}:{today}`
4. Firebase Auth record **last**, so the ID token stays valid through the earlier steps

It **fails closed**: without `FIREBASE_SERVICE_ACCOUNT` it returns 503 and deletes nothing. It is
idempotent and safe to retry. This is a well-built deletion path and satisfies Apple Guideline
5.1.1(v).

### What deletion does NOT reach

| Residue | Lifetime | Severity |
|---|---|---|
| `sec:inputs:{date}` — up to 200 chars of the user's prompts, keyed to their UID | Up to 48h after deletion | See G-01 |
| `sec:req:{date}`, `sec:rl429:{date}` — UID-keyed counters | Up to 48h | Low |
| `sec:auth401:{date}` — IP-keyed | Up to 48h | Low |
| `ana:{date}` — feature-usage events (not UID-keyed) | Up to 35 days | Low |
| `aispend:{date}` — aggregate only | 90 days | None |
| **localStorage on other devices the user signed in on** | Indefinite until that device is used again | See G-05 |
| **Firestore backups / PITR** | **UNVERIFIED** | See G-02 |
| Sentry events already captured | Per Sentry retention — **UNVERIFIED** | Low |
| SendGrid delivery records for mail already sent | Per SendGrid retention — **UNVERIFIED** | Low |

## 6. Summary of what the legal documents may and may not claim

**May claim (code-verified):**
- No sale of personal data; no targeted advertising; no advertising SDKs
- No tracking across apps or websites; no IDFA; no ATT prompt required
- HealthKit is write-only — Centerpost never reads Apple Health data
- No push tokens; notifications are local-only
- Journal is encrypted at rest with AES-GCM-256 under a PBKDF2 key (310,000 iterations,
  per-user random salt) derived from a PIN that is never stored
- Firestore rules restrict `users/{uid}/data/*` to the owner
- A working, fail-closed, in-app account deletion path exists
- Journal, mood, check-in and urge data are never bundled into AI prompts by the app
- Transport is HTTPS with HSTS; security headers and a CSP are deployed

**May NOT claim without a code change first:**
- "We honour Global Privacy Control" — no GPC handling exists (G-03)
- "We do not track email opens" — not disabled in code (G-04)
- "Your AI conversations are not retained by us" — 48h of prompt snippets are (G-01)
- "Deleting your account removes all your data everywhere immediately" — see §5 residue
- End-to-end encryption of anything — the journal PIN is an access control, not E2EE, and the
  code's own comments say so
- Any specific backup retention window until G-02 is answered
